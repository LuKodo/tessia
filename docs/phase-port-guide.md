## Hard rules
- No dry-run, no `--live`, no confirmation prompts (S1). Commands act directly.
- Never open `*.env`, `*.env.bak`, `tessia.windows.env` or any credential file. Never contact a real external system (Medicar, TheFactory, CPScan, SISPRO, Mutual Ser/ZonaSer, MIPRES, validator, Cassandra): all external I/O is tested against local mock servers (`tiny_http`, ephemeral ports) or in-memory fakes (`MemoryStore`, `MemoryNt`). Do not run the Go binary, `go build` or `go test`.
- Do not touch the containers `nt-redis-test`, `backend-postgres-1`, `mysql-server`. Tests use `TestDb` (Postgres at `TESSIA_TEST_PG_ADMIN_URL`, default `postgres://postgres:postgres@127.0.0.1:55432/postgres`) and the test Redis (`TESSIA_TEST_REDIS_URL`, default `redis://127.0.0.1:56379`).
- Files between phases go through `Artifacts` (bucket + `artefactos` index) and the per-machine `Workdir`; the per-invoice phase state goes through `ProcesoStore` (claim with `start_all`, write with `save_outcome`, exactly the Go semantics and state/reason strings); cross-host exclusion goes through `Leases`; NT data through `NtCatalog`; shared state through the stores in `docs/architecture.md`. Never reintroduce local `.lock` files or direct filesystem hand-offs between phases.
- User-facing text (console lines, states, reasons, error messages that Go prints) stays Spanish and IDENTICAL to Go where Go's output is a contract (reason codes like `REVISION_MANUAL` motivos are stored and shown by other tools). Code, comments, tests, commit messages: English. `println!` only for user output; diagnostics through `tracing`.
- Faithful port of the behavior, simplest implementation (S7). Output formats the Go docs call byte-compatible (Gson JSON, XML text edits, ZIP entry order, file names) must stay byte-compatible: assert it in tests using synthetic fixtures. Copy a Go golden/fixture only if it is clearly synthetic (no real patient/company data); otherwise build your own.
- Sync Rust: worker pools with `std::thread`/`crossbeam-channel`, `reqwest::blocking`, Diesel on the r2d2 pool. Use the foundation's `http` helpers (retry, `AdaptiveLimiter`, client builder, Medicar browser UA) rather than re-implementing them. Use the exact pool sizes, timeouts, retry counts and limiter numbers the Go docs/code state (they appear in the catalog as constants; re-read them in Go).
- No `unwrap()/expect()` in non-test code. Small functions. Reuse existing helpers for shared state (invoice normalization, outcome writing); never re-implement them with another shape. No new traits unless a test seam truly needs one.
- Every command/option you add has `--help` text (Spanish) and is wired in your own `src/phases/<name>/cli.rs`; `src/cli.rs`, `src/main.rs`, `src/context.rs` and other modules belong to the parent: if you need a change there, do NOT make it, report it in your Return.
- Each phase exposes, besides the CLI `run`, `pub fn run_phase(ctx: &AppContext, req: &PhaseRequest) -> anyhow::Result<PhaseReport>` (see `phases/common.rs`), which `proceso run` will call per invoice or per batch. Go's `proceso run` invokes each standalone command with `--invoices <one>` plus the phase flags: keep that behavior reachable through `PhaseRequest`.
- Migrations: only in your timestamp band (`migrations/2026-10-23-<NN>0000_<name>/`, NN from `docs/architecture.md`), tables in your own module with its own Diesel `table!` definitions. Do not edit other writers' migrations.
- Cargo.toml: you may append dependencies you really need to `[dependencies]`/`[dev-dependencies]` (one per line, alphabetical position is not required); the parent resolves merge conflicts. Do not change existing lines.
- Test-first where cheap; tests assert every observable effect (output, exit/return value, persisted rows, artifact keys), cover the cases the rule itself names, and go through the public interface. Tests are hermetic and parallel-safe (unique DB per test, ephemeral ports). Do not fabricate RED/GREEN evidence.
- Advisory only: about 400 changed lines per commit is a planning heuristic; never split artificially, delete comments, or drop tests to fit it.

Most phases read the convenio dataset (invoices and their lines). That store is being ported in parallel as task T1b (branch `feat/go-port-postgres` once merged; API documented in `docs/architecture.md` under "Dataset store"). So:
- **Phase A (start now):** everything that does not need the dataset store: HTTP clients, pure logic, parsers, your own tables/migrations, mock servers, CLI args, and the parts of `run_phase` that do not read the dataset, all with tests. For what you need from the dataset, define your own small input structs (documented) so Phase B is a thin adapter. Commit. When only dataset-dependent work remains, STOP and return `status: phase-a-done` listing exactly what is left (files, functions, behavior IDs). If your phase needs nothing from the dataset, finish everything and return `done`.
- **Phase B (the parent messages you):** run `git merge feat/go-port-postgres` inside your worktree (expect conflicts only in `Cargo.toml`/`Cargo.lock`/`config/keys.rs`; resolve by keeping both sides), read the "Dataset store" section of `docs/architecture.md`, finish the remaining work, then return `done`. Never rebase.
