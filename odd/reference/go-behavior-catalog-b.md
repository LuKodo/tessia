# Catalog of behaviors: CUV, DER, FEV, RAD, RIPS, SIE, SOP, TF, OTH

**Method.** I read docs/{cuv,derechos,fev,radicacion,rips,siesa,soporte,thefactory}.md and checked them against `cmd/tessia/cmd_*.go` and the spot-check files named below. CodeGraph was not usable because the repo has no `.codegraph/`. I did not trace the full call graph of `internal/*`.

**Convention.**
- Paths are relative to `/Users/adatospharma/Desktop/TessiaAutomatic/tessia`.
- "Live" means `--live`, which also calls `app.ConfirmLive` and asks for `SI` unless `--yes` is given.
- Without `--live`, every command is a dry-run that records the planned action in `dryrun-out/` and sends or writes nothing.
- Per-invoice state goes to `tessia.proceso_estado` (MySQL), one row per invoice and phase, with `DONE`, `FAILED` (retried), `REVISION_MANUAL` (skipped unless `--invoices`) and `EN_PROGRESO`.

**Discrepancy between docs and code.** The docs say `convenio.json` is the dataset. The code reads the dataset from MySQL cargue tables, keyed by the load folder name (`app.datasets()`, `cmd/tessia/dataset_tables.go:22-40`). Without `mysql.tessia_dsn` these commands fail with `errNoDatabase`, even in dry-run: `derechos`, `rips`, `soporte`, `fev verificar`, and `thefactory` (for the SSC lookup only). `docs/rips.md` still says `derechos.json`, but the code reads `<load>/derechos/<invoice>.json` (`cmd_rips.go:84`).

## [TF] `thefactory descargar` — download invoice XML and PDF from The Factory, plus the CPScan support
Depends on: the dataset of the load (convenio preparar) for the invoice list and SSC. Feeds `cuv generar`, `soporte generar`, `radicacion` step 1 and `fev`.

- TF-01 — `tessia [--live] thefactory descargar [--invoices a,b] [--workers N] <folder>`; invoices come from `--invoices`, else from the dataset; workers default 30, max 30, otherwise an error. [src: cmd/tessia/cmd_thefactory.go:86-94,104-112] [ext: MySQL]
- TF-02 — XML is fetched with `POST {thefactory.base_url}/api/archivos/GenerarContenedor` (member `ContenedorXml`, Base64 DIAN `AttachedDocument`). PDF is fetched with `POST .../api/archivos/DescargaPDF` (member `documento`). Both send `{tokenEmpresa, tokenPassword, documento}`. [src: internal/adapters/thefactory/client.go:5-6,58-60] [ext: TheFactory]
- TF-03 — Retry rule: at most 3 attempts. Only 408, 429 and 5xx retry (as HTTP status or JSON `codigo`), and so does an empty 200. The pause is 700 ms + 350 ms × attempt + 100–450 ms jitter, and no limiter slot is held while sleeping. [src: client.go:136-139,269-276] [ext: TheFactory]
- TF-04 — Result classification. `NO_DISPONIBLE` covers HTTP 204/404, `codigo` 204/404, or a `mensaje` containing NO DISPONIBLE / NO ENCONTRADO / NO EXISTE / NO HA VIAJADO / DIAN+NO / PENDIENT; it also covers a missing document member, and a 401 with a JSON body. `ERROR` covers a network error, non-JSON body, invalid Base64, or a failed check. [src: client.go:280-290; docs/thefactory.md:97-101] [ext: TheFactory] [note: classification is copied from Java and untested against real responses (open question 1)]
- TF-05 — Validity checks: XML must be at least 40 bytes and well-formed. PDF must be at least 1024 bytes (also requires the `%PDF-` header per docs). [src: cmd_thefactory.go:79; docs/thefactory.md:91] [ext: none]
- TF-06 — XML clean-up at download, two text edits only (byte-for-byte with Java). Remove the `AdditionalInformation` blocks COPAGO, CUOTA_MODERADORA, PAGOS_COMPARTIDOS and ANTICIPOS together with their preceding whitespace. In each `cac:PrepaidPayment`, set `schemeID` on the first `cbc:ID` from `cbc:InstructionID`: ANTICIPO → 04, PAGO(S) COMPARTIDO(S) → 03, CUOTA → 02, COPAGO → 01, anything else → 04. [src: internal/fevxml (NormalizeDownload); docs/thefactory.md:77-81] [ext: none]
- TF-07 — Outputs: `<F>.xml`, `<F>.pdf` and `XML/<F>_XML_PDF.zip` (entries `<F>.pdf` then `<F>.xml`). Files are written atomically with mode 0600. An invoice is complete when the XML is non-empty, the PDF is over 1024 bytes and the ZIP exists. Complete invoices are never re-downloaded (`YA_EXISTE`). [src: docs/thefactory.md:26-35,89-90] [ext: none]
- TF-08 — Console output is one line per invoice (`XML=… PDF=… ZIP=OK|YA_EXISTE|FALTA`) plus `complete=N incomplete=M`. Unavailable invoices do not make the command fail. [src: docs/thefactory.md:102-103] [ext: none]
- TF-09 — Throttling: one adaptive limiter per process (min 4 / initial 20 / max 30, window 100, pause 40–900 ms), backing off on 429, 5xx and timeouts. The 60 s request timeout starts after the slot is granted. [src: docs/thefactory.md:104-108] [ext: TheFactory] [note: numbers are the legacy `ReguladorDescargaAdaptativo.THE_FACTORY` values]
- TF-10 — Live needs `thefactory.base_url`, `thefactory.token_empresa`, `thefactory.token_password`, `cpscan.base_url`, `cpscan.bucket_url` and `mysql.tessia_dsn`. It takes `<folder>/.tessia-thefactory.lock`. Dry-run makes no request (the endpoints are credentialed POSTs) and writes nothing. [src: cmd_thefactory.go:170; docs/thefactory.md:110-114] [ext: MySQL]
- TF-11 — State (phase `thefactory`). XML, PDF and ZIP all present gives `DONE`. Anything missing gives `FAILED`, with the motivo set to the status line. Every invoice of the run is recorded, including `YA_EXISTE`. [src: docs/thefactory.md:140-145] [ext: MySQL]
- TF-12 — CPScan lookup runs in the same worker as the XML/PDF download. The SSC is the `No. SSC` of the first dataset line. It calls `GET {cpscan.base_url}/documentos/{ssc}` and downloads the support using this rule: `adicional` URL first, else by `origen`. PC needs an `adicional`. APP/BUCKET/empty use `formula-<ssc>.jpg`. SL tries `firma-<ssc>.jpg`, then `.png`, then the formula. [src: internal/soporte/acquire.go:139-198] [ext: CPScan]
- TF-13 — CPScan results are written as `CPSCAN/<F>.support.<pdf|jpg|png>` (kind detected from bytes) plus the sidecar `CPSCAN/<F>.cpscan.json` (`ssc, documento, origen, adicional, estado, archivo, ext, consultado`). The sidecar is written last. "CPScan has nothing" is stored with `archivo: ""`, and a transient failure writes nothing. [src: docs/thefactory.md:37-69] [ext: CPScan] [note: deleting the sidecar is the documented way to force a new lookup]
- TF-14 — CPScan never changes the invoice's own outcome. "No support" is `DONE` with the reason `CPSCAN sin soporte (SSC …)`. A transient failure is `DONE` with `CPSCAN pendiente (SSC …): …`. A re-run fetches only the missing CPScan part, not the XML/PDF/ZIP. An invoice with no SSC or no dataset only loses the CPScan part. [src: docs/thefactory.md:57-67,147-150] [ext: CPScan]
- TF-15 — CPScan downloads share one adaptive limiter (6/24/35, window 100, pause 25–700 ms), a 30 s download timeout, and `cpscan.ca_file` / `cpscan.tls_server_name` TLS options. Non-http(s) `adicional` URLs are rejected. [src: docs/soporte.md:199-202,244; docs/thefactory.md:55] [ext: CPScan]

## [CUV] `cuv generar` — send FEV + RIPS to SISPRO and write the CUV TXT
Depends on: `<F>.json` from `rips generar`, `<F>.xml` or the XML_PDF zip from `thefactory descargar`, and `proceso_estado` for the gates. Feeds `radicacion` step 2.

- CUV-01 — `tessia [--live] cuv generar [--invoices a,b] [--workers N] <folder>`. Workers default 40, max 40. Requires config `minsalud.numero_contrato` and `company.codigo_prestador` even in dry-run. Live also needs `minsalud.base_url`, `tipo_doc`, `numero_doc`, `clave` and `nit`. [src: cmd/tessia/cmd_cuv.go:65-83,189] [ext: none]
- CUV-02 — Invoice discovery: the invoices are the `<F>.json` files in the folder, matching `^[A-Za-z]{2,4}[0-9]+\.json$`. With `--invoices`, one without a JSON gives a typed error. When several are requested, the unknown ones are only warned about. [src: cmd_cuv.go:55,86-119] [ext: none] [note: the regexp constrains invoice-number format]
- CUV-03 — Gates, applied only without `--invoices`: skip when the invoice's own cuv state is `REVISION_MANUAL`. Skip when its `rips` state exists and is not `DONE` (`RIPS_NO_OK`); no `rips` state means it is still sent. With `--invoices`, it is re-sent whatever its state. [src: cmd_cuv.go:130-147; docs/cuv.md:155-160] [ext: MySQL]
- CUV-04 — Skip codes. `YA_TIENE_CUV` (a valid CUV is already in `<F>.txt`) is recorded as `DONE`. `XML_FALTA` is `FAILED`. `XML_SIN_CONTRATO` and `RIPS_INVALIDO` are `REVISION_MANUAL`. [src: cmd_cuv.go:288-300] [ext: none]
- CUV-05 — XML source: `<F>.xml`, else restored from the `<F>.xml` entry of `XML/<F>_XML_PDF.zip` (or `ZIP/`). [src: docs/cuv.md:33-34] [ext: none]
- CUV-06 — XML adjustment before sending (`fevxml.PrepareMinisterio`), text edits in Java order and byte for byte:
  - `NUMERO_CONTRATO` 22382 is replaced by `minsalud.numero_contrato`.
  - Missing `Usuario` fields are added: `CODIGO_PRESTADOR`, `MODALIDAD_PAGO` (schemeID 04), `COBERTURA_PLAN_BENEFICIOS` (régimen 01 → 16, 04 → 17; an existing one is set unless its scheme is 02), `NUMERO_CONTRATO`, and an empty `NUMERO_POLIZA`.
  - Field `22` is removed, and `FACTURA_SIN_CONTRATO` is re-inserted after `NUMERO_POLIZA`.
  - The copago/cuota/anticipo fields are removed and the `PrepaidPayment` schemeID is set.
  - Every `InvoicePeriod` / `AuthorizationPeriod` `StartDate` becomes the constant `2025-01-01`.

  [src: internal/fevxml/fevxml.go:29; docs/cuv.md:35-52] [ext: none] [note: `2025-01-01` is hardcoded (open question 6). The adjustment is not idempotent: every run re-inserts `FACTURA_SIN_CONTRATO` and adds one blank line, and Go reproduces that. An XML without `NUMERO_CONTRATO` is skipped as `XML_SIN_CONTRATO` instead of Java's DOM rewrite.]
- CUV-07 — Period error: if a start date still differs after the edits, the earlier edits are kept, the ZIP is not refreshed and the XML is sent anyway (printed as `aviso`). [src: docs/cuv.md:49-52] [ext: none]
- CUV-08 — Régimen comes from `usuarios[0].tipoUsuario` of `<F>.json`, with the replacements EPS048/EPSS48/ESS207/ESSC07. A changed XML is written back to `<F>.xml`, and the XML entry of `<F>_XML_PDF.zip` is replaced (other entries kept, XML appended last). [src: docs/cuv.md:53-58] [ext: none]
- CUV-09 — Payload is `{"rips": <bytes of F.json>, "xmlFevFile": Base64(XML)}`. [src: docs/cuv.md:59] [ext: SISPRO]
- CUV-10 — Auth: `POST {base}/api/Auth/LoginSISPRO` with `{persona:{identificacion:{tipo,numero}}, clave, nit}`. Login retries default to 3 tries with doubling backoff and ±25% jitter. The JWT is cached until one minute before `exp`. A login with no token gives `Token vacío` and nothing is sent. [src: internal/adapters/sispro/client.go:138-160; docs/cuv.md:60-63] [ext: SISPRO]
- CUV-11 — Send: `POST {base}/api/PaquetesFevRips/CargarFevRips` with a Bearer token. It is never retried (as in Java). The request timeout is 210 s, counted after the limiter slot is granted. [src: docs/cuv.md:64-65,114-119] [ext: SISPRO] [note: TLS is verified, unlike Java. `minsalud.ca_file` or `minsalud.tls_pin_sha256` is needed for the local SISPRO server, whose certificate is `CN=localhost`.]
- CUV-12 — Throttling: one adaptive limiter per process (8/20/40, window 80, pause 25–900 ms) shared by login, `CargarFevRips` and `ConsultarCUV`. Concurrency is `--workers` invoices in flight. [src: docs/cuv.md:114-119] [ext: SISPRO]
- CUV-13 — Response interpretation (`cuv.Interpret`). The body is parsed like Gson `RespuestaValidacion`. 200/201 gives `<F>.txt`, and 400 gives `<F>_ERROR.txt`. A `NumFactura` belonging to another invoice (trim, strip `-`, upper-case) gives `<F>_RESPUESTA_NO_CORRESPONDE.txt`. Any other status, an unparseable body, or Java NPE cases (200 with a result without `Clase`, 400 without `ResultadosValidacion`) write nothing and only print a line. [src: docs/cuv.md:7-25,66-74] [ext: SISPRO]
- CUV-14 — Rejection reason recorded in state (a Tessia addition). When there are `RECHAZADO` results and no CUV, the motivo is `"RECHAZADO" - "RVG01" - "<PathFuente>"` per result, joined by ` | `, at most 5, then ` | +N mas`. `(RVG18: CUV existente)` is appended if the sweep found a CUV. [src: docs/cuv.md:75-82] [ext: none]
- CUV-15 — Final-sweep rewrite of the TXT (`cuv.Sweep`, equivalent to Java's `barrerTxtCuvMinisterioAlFinalizar`). `ResultState` is forced to `true` even on rejected responses. `NumFactura` becomes the last segment of `RutaArchivos`. For RVG18, `Observaciones` becomes `CodigoUnicoValidacion`, `ProcesoId` comes from `POST /api/ConsultasFevRips/ConsultarCUV`, and `ResultadosValidacion` becomes `[]`. Nulls are dropped. [src: docs/cuv.md:83-90] [ext: SISPRO] [note: an RVG18 response arriving as HTTP 400 lands in `<F>_ERROR.txt`, which radicacion ignores (open question 1)]
- CUV-16 — Output encoding: the first write is Gson `serializeNulls + disableHtmlEscaping + prettyPrinting` in model field order. The sweep rewrites without `serializeNulls`, keeping member order and number literals. Files are UTF-8 with no trailing newline, atomic, mode 0600. [src: docs/cuv.md:92-100,116] [ext: none] [note: the Java sweep used the platform charset, so the Go output is UTF-8 only (open question 4)]
- CUV-17 — Live takes `.tessia-cuv` locks (per-invoice claims, 2 h TTL) via `acquirePhaseLock`. Dry-run builds every payload and prints the plan, makes no request (not even `ConsultarCUV`, which is a POST with a token), writes nothing, and records only sizes. [src: cmd_cuv.go:170-199] [ext: none]
- CUV-18 — State (phase `cuv`). `DONE` for a TXT with a CUV. `FAILED` for `XML_FALTA`, network or token errors, and 5xx. `REVISION_MANUAL` for `XML_SIN_CONTRATO`, `RIPS_INVALIDO`, a 400 `_ERROR.txt`, `RECHAZADO` codes, and `_RESPUESTA_NO_CORRESPONDE.txt`. Live requires `mysql.tessia_dsn`. [src: docs/cuv.md:149-167] [ext: MySQL]
- CUV-19 — Token-failure alert for a standalone run. After outcomes are saved, if token-less logins exceed a percent of submitted invoices (default 50%, minimum sample 4, overridable from the stored preparation parameters) the run returns an error. Invoice states are unchanged. [src: cmd_cuv.go:505-526; internal/cuv/availability.go:43-51; internal/convenio/parameters.go:32-33] [ext: MySQL, SISPRO] [note: undocumented in docs/cuv.md]
- CUV-20 — Not ported: credit/adjustment notes (NA/NC), the EventoSAS_Premium flow, and the manifest. Java's `Historico` calls are commented out in the original and not needed. [src: docs/cuv.md:169-185] [ext: none]

## [CUV] `cuv barrer` — folder-wide TXT sweep (Java `Vista_ActualizarCUVMinisterioLocal`)
Depends on: TXT files already in the folder. Config for SISPRO is needed only when a file has RVG18.

- CUV-21 — `tessia [--live] cuv barrer <folder>` rewrites every `<folder>/*.txt` that is a JSON object (Gson pretty, no nulls, sequential). It sets `ResultState` to `true`. `NumFactura` is the last `\` part of `RutaArchivos`: no trim, `/` is not a separator, `""` stays `""`. [src: cmd/tessia/cmd_cuv_barrer.go:44; docs/fev.md:71-80] [ext: none]
- CUV-22 — RVG18 handling: the first RVG18 result puts its trimmed `Observaciones` (even `""`) in `CodigoUnicoValidacion`, `ProcesoId` comes from `ConsultarCUV`, and `ResultadosValidacion` becomes `[]`. [src: docs/fev.md:79-82] [ext: SISPRO]
- CUV-23 — Non-JSON TXTs are left untouched. Files Java could not process (a result that is not an object, a path of only `\`) are reported as `ERROR` and not written. [src: docs/fev.md:85-88] [ext: none] [note: the rule set differs from `cuv generar`'s end sweep]
- CUV-24 — A rewritten TXT that now has a CUV is recorded `DONE` in phase `cuv`, with the motivo `RVG18: CUV existente` for RVG18 fixes. Live asks for confirmation and takes the `.tessia-cuv` folder lock (2 h). Dry-run makes no request and writes nothing. [src: cmd_cuv_barrer.go:117-124; docs/fev.md:83-91] [ext: MySQL, SISPRO]

## [FEV] `fev ajustar` / `fev verificar` — support edits and value check
Depends on: XML/ZIP from `thefactory descargar`; `verificar` needs the dataset in MySQL. Feeds `rips generar` and `conciliar` through the `fev_valor` state.

- FEV-01 — `tessia [--live] fev ajustar --op cucon|cuota [--cucon V] [--invoices a,b] <folder>`. Targets are every `<folder>/*.xml` plus every `.xml` entry in `<folder>/*.zip`, `XML/*.zip` and `ZIP/*.zip`. Each XML is edited where it is stored; a changed ZIP entry is replaced and the XML is appended last. `--invoices` matches `<F>.xml` and `<F>[_XML_PDF].zip`. [src: cmd/tessia/cmd_fev.go:155-199; docs/fev.md:20-26] [ext: none]
- FEV-02 — `--op cucon`: when `NUMERO_CONTRATO` is `22382` it becomes the CUCON (trimmed, XML-escaped). The CUCON is `--cucon` or `minsalud.numero_contrato`. Counters are `modificados`, `sin_contrato` and `contrato_diferente`. [src: cmd_fev.go:174-177; docs/fev.md:27-30] [ext: none] [note: the literal `22382` is the "old contract" marker in the code. The Java screen's CUCON value is deliberately not in the code.]
- FEV-03 — `--op cuota`: runs only when the XML has an anticipo to legalize (an `ANTICIPOS` value other than 0, or `PrepaidPayment/PaidAmount` > 0). Every non-empty `PrepaidPayment` `cbc:ID` gets its `schemeID` (anticipo 04, pagos compartidos 03, cuota 02, copago 01, default 04), and `ANTICIPOS` is removed. `ADVERTENCIA` lines are printed when `PrepaidAmount` is missing or differs from the `PaidAmount` sum. [src: docs/fev.md:31-36] [ext: none] [note: overlaps with TF-06, whose ID pattern differs slightly (open question 2)]
- FEV-04 — State (phase `fev_ajuste`): `DONE` with the counters it fell in (`cucon: modificado`, `cuota: sin_cambios`, …), `FAILED` if a file cannot be read or written. XML read from a zip entry is capped at 256 MiB. Live takes the per-invoice `.tessia-cuv` locks (2 h), shared with `cuv generar`. [src: cmd_fev.go:61,277-281,376; docs/fev.md:37-44] [ext: MySQL]
- FEV-05 — `tessia fev verificar [--invoices a,b] <load folder>` compares the XML total with the convenio total per invoice. The XML total is the first `PayableAmount` or `TaxInclusiveAmount` of `LegalMonetaryTotal` in the CDATA invoice (from the first `.xml` entry of `XML|ZIP/<F>_XML_PDF.zip`, else `<F>.xml`). If the text has both `,` and `.`, the `,` is a thousands separator; a lone `,` is the decimal separator. [src: cmd_fev.go:392-406; docs/fev.md:48-53] [ext: MySQL]
- FEV-06 — Convenio total is the sum of line `vlr. total` values (`$` and spaces removed, `1.234,56` becomes `1234.56`). One unreadable value makes it `NO_DISPONIBLE`. `OK` when |difference| < 0.01, otherwise `VALOR_DIFERENTE` or `XML_SIN_VALOR`. [src: docs/fev.md:54-57] [ext: none]
- FEV-07 — `verificar` writes no file. Live records phase `fev_valor`: `OK` gives `DONE`, `VALOR_DIFERENTE` gives `REVISION_MANUAL` (motivo `VALOR_DIFERENTE XML=… convenio=…`), `XML_SIN_VALOR` gives `FAILED`. The exit code is 1 when any invoice is not `OK`. Every run re-checks all invoices. [src: docs/fev.md:58-63] [ext: MySQL] [note: Java's `_VALOR_DIFERENTE.txt` and the legacy log flag reset are not written. The block is enforced only via the `fev_valor` state read by `rips generar`.]

## [DER] `derechos validar` — affiliate rights (régimen, zona, DANE, sexo, birth date)
Depends on: dataset of the load (MySQL), `convenio preparar`. Feeds `rips generar`. In `proceso run`, it runs right before `rips`.

- DER-01 — `tessia [--live] derechos validar [--invoices a,b] [--concurrency N] [--cache-ttl D] <load folder>`. Defaults are concurrency 30 and TTL 24h. Without `--invoices`, `derechos.Select` picks the pending invoices from the dataset and previous states. `REVISION_MANUAL` invoices are skipped unless named. [src: cmd/tessia/cmd_derechos.go:52-109; docs/derechos.md:42-43] [ext: MySQL]
- DER-02 — Each invoice must belong to exactly one affiliate. A dataset that breaks this fails the command before any query (the error names the invoice, not the documents). The validator is queried once per distinct `tipo|documento`. [src: docs/derechos.md:10-15; cmd_derechos.go:108] [ext: none]
- DER-03 — Validator auth: a Keycloak password grant at `derechos.token_url`, cached until 30 s before `expires_in`. Then a FHIR `Parameters` request with `documentType` and `documentId` goes to `derechos.validate_url`. [src: docs/derechos.md:108-111; internal/adapters/derechosapi] [ext: Mutual Ser validador / Keycloak]
- DER-04 — Field mapping from the FHIR patient: régimen from the extension `mutualSER/hl7/patient/healthModality` (`SUBSIDIADO` gives `04`, else `01`). Zona from the zone extension (empty or containing `Urb` gives `U`, else `R`). Municipio is the DANE code from `address[0].city`, first `|` part. Sexo is male `M`, female `F`, other `I`. Birth date is as returned. [src: docs/derechos.md:17-23] [ext: Mutual Ser validador]
- DER-05 — Document-type fallback on HTTP 400–410: `TI → CC`, and `RC → TI → CC`. After the fallbacks, 400–410 counts as "not found". [src: docs/derechos.md:112] [ext: Mutual Ser validador]
- DER-06 — Retries: transport errors, 5xx and 429 via `httpx.Do`, 4 attempts with backoff. The limiter is `derechos` (4..`--concurrency`, initial 16, window 80, pause 25–900 ms) plus a worker pool of `--concurrency`. HTTP timeout is 30 s. [src: cmd_derechos.go:188-198; docs/derechos.md:113-117] [ext: Mutual Ser validador]
- DER-07 — The validator is mandatory (no fallback to CSV columns). Outcomes per invoice (phase `derechos`):
  - Complete rights give `DONE`.
  - Not found gives `REVISION_MANUAL` with `Afiliado no encontrado en validador de derechos Mutual Ser`.
  - A technical failure gives `REVISION_MANUAL` with `Validador de derechos no disponible`.
  - Incomplete data gives `REVISION_MANUAL` with `Datos de derechos incompletos: faltan <campos>`.
  - A missing document type or number gives `REVISION_MANUAL` with `Factura sin tipo o numero de documento del afiliado`.

  [src: docs/derechos.md:25-34] [ext: MySQL] [note: user decision of 2026-09-25. The CSV `causal exento`, `departamento` and `municipio` columns are never used as fallback. CSV sex and birth date are only cross-checked, and differences are logged by field name; the validator wins.]
- DER-08 — Token renewal is single-flight on 401: only the rejected token is dropped (compare-and-invalidate) and the request is resent once. A 401/403 after renewal, or a failed token fetch, is `ErrAuthentication`. That stops dispatching, cancels in-flight calls, saves the invoices already resolved, restores the unresolved ones to their previous state (removing `EN_PROGRESO`), prints how many were left untouched, and exits with an error. [src: cmd_derechos.go:266-288; docs/derechos.md:121-141] [ext: Mutual Ser validador]
- DER-09 — One validator client per process is shared by every call (`App.sharedDerechosClient`). The limiter ceiling is the `--concurrency` of the call that builds it. In `proceso run`, an authentication stop is fatal: the context is cancelled even with `--continue-on-error`, and it is never recorded as "Validador no disponible". [src: cmd_derechos.go:201-224; docs/derechos.md:142-158] [ext: none]
- DER-10 — Validator-down alert: if technical failures exceed a percent of queried affiliates (default 50%, minimum sample 4, overridable from stored parameters; cache hits do not count) the command returns an error after saving outcomes. ## Dependency map
- File chain, one phase per system:
  - `convenio preparar` writes the dataset to MySQL cargue tables.
  - `thefactory descargar` writes `<F>.xml`, `<F>.pdf`, `XML/<F>_XML_PDF.zip` and `CPSCAN/*`.
  - `derechos validar` writes `derechos/<F>.json`.
  - `fev verificar` writes the `fev_valor` state.
  - `rips generar` writes `<F>.json`.
  - `cuv generar` writes `<F>.txt` or `_ERROR.txt`.
  - `soporte generar` writes `CRC/CRC_<nit>_<F>.zip`.
  - `radicacion run` uploads all of these in four steps.
- The coupling between phases is `proceso_estado` rows (`derechos`, `fev_valor`, `rips`, `cuv`, `thefactory`, `soporte`, `fev_ajuste`). These are read by the gates in `rips generar` (RIPS-03) and `cuv generar` (CUV-03).
- MySQL (`mysql.tessia_dsn`) is required for the dataset, all state rows, the rights cache, `radicacion_estado`, `factura_valor_xml`, `portal_cargue*`, and stored alert thresholds.
- HTTP systems: TheFactory (XML/PDF), CPScan (support), Mutual Ser validador with Keycloak (rights), SISPRO (CUV), Mutual Ser ZonaSer (radicación), Siesa Connekta (accounting).
- Fixed contract and constants: `minsalud.numero_contrato` (CUV, FEV cucon), the contract marker `22382` (CUV-06, FEV-02), the period start `2025-01-01` (CUV-06), the constants `031` and `30` days in RIPS (RIPS-08), the deposit list (SOP-06), and the Siesa defaults (SIE-04).
- Commands outside this group that depend on these: `conciliar` (rebuilds lines and resets `fev_valor`), `proceso run` (calls derechos, thefactory, rips, cuv, soporte and radicacion per invoice), and `migrate retire-log` (backfills `radicacion_estado` and phase states).

## Key Learnings
1. The CLI reads each load's dataset from MySQL cargue tables keyed by the load folder name (`app.datasets()`), so docs that mention `convenio.json` are stale for derechos, rips, soporte, fev verificar and thefactory.
2. Every command is a dry-run unless `--live` is given, and live mode adds an interactive `SI` confirmation, a phase lock, and `proceso_estado` writes that require `mysql.tessia_dsn`.
3. Phases are coupled only through files in the load folder and through `proceso_estado` states, such as `fev_valor` and `rips`, which `rips generar` and `cuv generar` read as gates when `--invoices` is not given.
4. `phaselock.go` creates per-invoice claim files (`<base>-<hash>.lock`) when an invoice list is passed and a folder-scoped `<base>.lock` otherwise, so the lock file names in the docs are simplified.
5. Many outputs are deliberately byte-compatible with the Java tool (Gson formatting, XML text edits, ZIP entry order), and the port verifies this through golden tests under `testdata/golden` generated by `tools/javagolden`.
